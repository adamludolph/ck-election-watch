## Problem Statement

Milestone 2 produces synthetic, evidence-backed draft statements and can publish
one through a fixture preparation script, but it has no operator workflow for
separately reviewing evidence, approving a statement, publishing it, or
unpublishing it. The current combined `approveAndPublishStatement` path makes
those editorial decisions too easy to collapse into one technical operation.

Milestone 3 must let a local operator inspect the complete evidence chain,
deliberately move a synthetic statement through review, approval, publication,
and unpublication, and verify that private editorial material never influences
or appears in public output.

## Why This Milestone

Three contained milestones were considered:

1. **Editorial review and publication controls — selected.** This closes the
   largest trust gap in the current evidence pipeline. It turns an internal
   fixture script into an inspectable human decision path without adding
   authentication or production exposure.
2. **Search — deferred.** Search would help public users find already-published
   material, but it does not make publication safer. It also introduces
   relevance and missing-result language that needs separate methodology review.
3. **Issue browsing — deferred.** The public candidate page already groups
   statements by controlled issue. A wider issue-browsing surface adds navigation
   and comparison risks without improving editorial accountability.

The contained milestone is one local review queue, one statement detail view,
and one complete state lifecycle. It does not add a general administration
system.

## Operator Value

A local operator can:

- see which synthetic statements require review;
- inspect `Statement → Evidence → Extraction → Normalized Content → Source
  Snapshot`;
- record a synthetic review outcome and private note;
- approve only a statement whose latest review outcome is ready;
- publish only an approved statement;
- unpublish an active publication with a reason;
- see the append-only editorial and publication timeline; and
- open the public candidate page to confirm the visibility change.

## Constraints

- Local and fixture-backed only. No production database, deployment, credential,
  live candidate, or network acquisition.
- No authentication, accounts, permissions, or real reviewer identity.
- Synthetic operator references exist only to prove private identifiers cannot
  leak.
- No rankings, comparisons, recommendations, inferred positions, automated
  summaries, semantic search, or methodology changes.
- Public pages continue to render immutable, digest-verified publication
  payloads rather than joining mutable editorial tables.
- The review route and all mutation actions fail closed in production mode.
- Existing Milestone 2 data upgrades through ordered, digest-checked,
  forward-only migrations.

## Premises

1. The next user is a local operator reviewing deterministic fixture data, not
   an authenticated production editor.
2. Review, approval, publication, and unpublication are separate decisions and
   must not be bundled into one action.
3. Append-only event rows are the audit record; mutable status columns and
   publication closure fields are projections used for efficient current-state
   reads.
4. Approval cannot return to draft or rejected; terminal withdrawal is its only
   outgoing decision-state transition. Publication creation revalidates the
   approved statement and freezes that fact into the immutable payload. A public
   response reads only active, digest-verified publication snapshots; it never
   re-joins mutable statements, drafts, private notes, synthetic operator
   references, or audit history.
5. Unpublication removes public visibility without deleting evidence, review
   history, the publication snapshot, or its event history.
6. Search and broader issue browsing are separate milestones because neither is
   required to prove the editorial lifecycle.

## Approaches Considered

### Approach A: Thin UI over existing status columns

Add a `/review` page and server actions that directly update `statements.status`
and `publications.withdrawn_at`.

- **Effort:** Small
- **Risk:** High
- **Pros:** Few files and the fastest visible result.
- **Cons:** No append-only review history, no durable unpublication record, and
  direct table updates make invalid transitions easy to introduce.
- **Reuse:** Existing publication functions and public candidate route.

### Approach B: Event-backed editorial service and local review UI

Add append-only editorial and publication event tables, keep current-state
columns as transactionally updated projections, and put every state change
behind one domain service. Build a production-disabled `/review` queue and
detail experience on that service.

- **Effort:** Medium
- **Risk:** Medium
- **Pros:** Explicit transition rules, durable history, clean privacy boundary,
  reproducible tests, and a narrow UI that matches the objective.
- **Cons:** Requires one forward migration, transaction design, and more
  negative tests than the thin-UI option.
- **Reuse:** `runStage`, `PublicationPolicyError`, payload verification,
  deterministic IDs, PGlite fixtures, current evidence components, and existing
  public queries.

### Approach C: CLI workflow plus read-only review page

Keep all mutations in a fixture CLI and make `/review` display evidence and
history without controls.

- **Effort:** Small to medium
- **Risk:** Medium
- **Pros:** Minimal mutation surface and easy scripting.
- **Cons:** Fails the required operator-facing end-to-end interaction and does
  not prove keyboard-accessible publication controls.
- **Reuse:** Existing `scripts/prepare-demo.ts` pattern.

## Recommended Approach

Choose **Approach B**. It is the smallest approach that satisfies every required
state, history, privacy, migration, accessibility, and end-to-end condition.
Approach A is a demo path without the audit guarantees. Approach C is
reproducible but does not deliver the required local review experience.

Approach B is staged as three verification checkpoints: migration and database
invariants first, domain transitions and public privacy second, then UI and
browser lifecycle. A failed checkpoint blocks the next stage.

The goal objective already authorizes this contained editorial milestone.
Implementation remains blocked until `/plan-ceo-review`,
`/plan-eng-review`, and `/plan-design-review` all approve the detailed plan.

## Editorial State Model

### Current-state projection

`statements.status` remains the current decision-state projection:

- `draft`
- `approved`
- `rejected`
- `withdrawn`

Publication activity is represented by the statement's single publication
record:

- no active publication
- active publication

The operator-facing editorial phase is derived deterministically from the
decision-state projection, active publication, and latest editorial event:

- `needs_review`: draft with no review event;
- `changes_requested`: draft whose latest review is
  `reviewed_changes_requested`;
- `ready_to_approve`: draft whose latest review is `reviewed_ready`;
- `approved_unpublished`: approved with no active publication and no prior
  unpublication;
- `published`: approved with an active publication; and
- `rejected`: rejected with no active publication; and
- `withdrawn`: previously published and now terminally unpublished.

“Latest” means the greatest `sequence`. `sequence` is a monotonic per-statement
integer allocated after locking the statement row inside the same transaction
as the event. `occurred_at` is supplied by a service-owned clock—real time in
the app and fixed time in fixtures/tests—and cannot be supplied by a form. A
unique `(statement_id, sequence)` constraint makes ordering independent of clock
resolution; the service rejects a timestamp earlier than the prior event.

### Append-only events

`statement_editorial_events` records:

- `reviewed_ready`
- `reviewed_changes_requested`
- `approved`
- `rejected`
- `withdrawn`

Each row stores the statement, server event time, required reason or note where
appropriate, a server-owned synthetic fixture operator reference, the previous/current
projected state, and `review_subject_sha256`. All editorial events, including
approval, rejection, and withdrawal, store the subject digest observed by that
decision.

`review_subject_sha256` canonically digests the statement summary, attribution,
controlled issue IDs/slugs/labels, candidacy ID/slug, evidence quote and offsets,
normalized block ID/text/digest, snapshot ID/digest, source title/original URL/
capture time, extraction identity, and attribution relationship. This is every
input that can affect the publication payload plus its provenance. Every review
event records it. Approval recomputes it and requires an exact match with the
latest `reviewed_ready` event, so stale review cannot approve changed evidence.

`publication_events` records:

- `published`
- `unpublished`

Each row stores the publication record, server event time, required unpublication
reason, and synthetic fixture operator reference. A `published` event also
stores the immutable `approved_editorial_event_id` whose subject digest was
matched; `unpublished` leaves that field null.

### Action input matrix

| Action | Required input | Optional input | Previous → current decision state | Projection change |
|---|---|---|---|---|
| `reviewed_ready` | request ID, statement ID, synthetic operator ref | private note, 1–500 chars | `draft` → `draft` | append current subject digest; phase becomes `ready_to_approve` |
| `reviewed_changes_requested` | request ID, statement ID, synthetic operator ref, private reason 1–500 chars | none | `draft` → `draft` | append current subject digest; phase becomes `changes_requested` |
| `approved` | request ID, statement ID, synthetic operator ref, approval reason 1–500 chars | none | `draft` → `approved` | require ready digest match; update status and `approved_at` |
| `rejected` | request ID, statement ID, synthetic operator ref, rejection reason 1–500 chars | none | `draft` → `rejected` | update status |
| `published` | request ID, statement ID, synthetic operator ref | publication reason, 1–500 chars | `approved` → `approved` | recompute the current subject digest, require it to match the latest `approved` editorial event's stored digest, then insert the immutable publication and `published` event |
| `unpublished` | request ID, publication ID, synthetic operator ref, unpublication reason 1–500 chars | none | `approved` → `withdrawn` | close publication projection, append events, invalidate approval |

All strings are trimmed. Empty, over-limit, or non-string values fail validation.
The server-action boundary assigns the synthetic fixture operator identifier;
browser-submitted form data cannot choose it. Operator references have a 1–100
character limit and are never selected by public code.

### Allowed transitions

1. `draft` → record `reviewed_ready`
2. `draft` → record `reviewed_changes_requested`
3. `draft` + latest review is `reviewed_ready` → `approved`
4. `draft` + latest review is `reviewed_changes_requested` → `rejected`
5. `approved` + no active publication → publish
6. `approved` + active publication → unpublish with reason

Disallowed transitions fail without adding a success event or changing the
current-state projection. Rejection and withdrawal are terminal. An unpublished
statement cannot be republished in this milestone; corrected evidence must enter
as a new extracted statement and complete a fresh review and approval lifecycle.

Every mutation accepts a caller-provided request ID. Editorial-event replay
keys use `(statement_id, action, request_id)`; publication-event replay keys
use `(publication_id, action, request_id)`. Exact replay returns the original
result without appending another event. Reusing a request ID with different
inputs raises `EditorialReplayConflictError`. Each event stores an
`input_fingerprint_sha256` over action, IDs, synthetic operator reference,
expected phase, and the complete private note/reason. `stage_runs.input_refs`
stores only safe IDs and that fingerprint, never private plaintext. The service
wraps each action in the existing `runStage` serializer, uses the request ID as
the stage idempotency key, and supplies `validateReplay` to compare the event's
stored fingerprint before returning cached output. Stale forms also submit their
expected phase and fail with
`EditorialTransitionConflictError` when current state has changed.

Each statement can create one immutable publication row, retaining the existing
one-publication-per-statement constraint and using the existing deterministic
publication identity. Unpublish
transactionally sets that row's closure projection (`withdrawn_at` and
`withdrawal_reason`), changes the decision state to `withdrawn`, and appends its
immutable publication and editorial withdrawal events.

## Persistence and Migration

Add one ordered migration after `0003_official_person_backfill.sql` that:

- creates `statement_editorial_events`;
- creates `publication_events`;
- adds indexes for statement timelines and active publication lookup;
- backfills a legacy `approved` editorial event and a `published` event for
  each existing Milestone 2 publication, plus an `unpublished` event for any
  already-closed publication;
- adds database checks for event types, state pairs, timestamps, and required
  reasons;
- uses each publication's already-verified immutable `payload_sha256` as the
  legacy approved subject digest, the existing publication timestamps, and the
  fixed synthetic actor `migration:milestone-2`;
- assigns deterministic SQL-safe request IDs
  `migration:publication:<publication-id>:<event-type>` and
  `migration:editorial:<statement-id>:<event-type>` so backfilled rows satisfy
  runtime replay schema and unique keys;
- for every already-closed publication, atomically changes an associated
  `approved` statement to `withdrawn` and appends a deterministic editorial
  withdrawal event with actor `migration:milestone-2`, the legacy subject
  digest, and its deterministic migration request ID;
- creates `BEFORE UPDATE OR DELETE` triggers on both history tables that raise
  an integrity error, after all migration backfill inserts are complete;
- creates a trigger that prevents updates to or deletion of publication snapshot
  identity, payload, digest, and publication time while allowing only the
  withdrawal projection to close.

Before backfill, the migration fails atomically with a named preparation error
when it encounters any ambiguous Milestone 2 shape:

- an `approved` statement without a publication;
- a publication whose statement is not `approved` or whose `approved_at` is
  missing;
- an approval timestamp later than its publication timestamp;
- `withdrawn_at` earlier than `published_at`;
- a withdrawal reason on an open publication; or
- a non-empty legacy withdrawal reason longer than the new 500-character bound.

A closed legacy publication with a null/blank reason is accepted and receives
the fixed event reason `Migrated legacy withdrawal without recorded reason.`;
the nullable Milestone 2 projection is preserved. These are the only legacy
exceptions. Tests cover every fail-fast condition and the fixed-reason path.

The migration creates an `active_publication_payloads` view that returns only
publication ID, statement ID, payload, digest, and publish time when a
`published` event references an immutable approved editorial event and no
`unpublished` event exists for that publication.
Public code reads this view. It does not trust mutable closure fields or select
private event columns.

Database checks enforce only row-local invariants. Cross-row chronology,
expected-state agreement, and projection updates are enforced by the
transactional editorial service and concurrency tests.

Migration tests must first prepare the exact merged Milestone 2 schema through
`0003`, insert representative Milestone 2 fixture data, then apply the new
migration and verify both history backfill and current public visibility.

## Privacy Boundary

Public code may read:

- candidacy and election display fields;
- completed public coverage fields;
- `active_publication_payloads` view rows and their digests; and
- controlled public issue labels.

Public code must not read:

- draft or rejected statements;
- statement editorial events;
- publication events;
- internal notes or reasons;
- synthetic operator references;
- raw extraction results;
- raw source snapshots; or
- normalized content except the excerpt already frozen into an active
  publication payload.

The current draft-sensitive absence branch is removed. A draft, review outcome,
private note, or audit event must not change the public response. Public absence
wording depends only on completed coverage and active publications.

Public code does not re-check `statements.status`. Publish revalidates approval
and the reviewed subject digest. Unpublish appends the immutable event that
removes the cycle from the view and terminally withdraws the statement. This
preserves the public-read boundary without weakening the “approved evidence
only” rule.

## Local Review Experience

### Queue: `/review`

- Page heading states that this is a local fixture review workspace.
- Four compact headline counts show needs review, ready to approve, approved
  unpublished, and published; all eight phases remain visible in filter
  navigation with their own counts.
- Each queue item shows candidate, issue, current state, source title, capture
  time, and latest decision. The queue never mutates editorial or publication
  state; its only primary action is `Inspect evidence`, implemented by the row
  link to detail.
- State is conveyed by text and icon as well as color.
- Filters are standard links for All, Needs review, Changes requested, Ready to
  approve, Approved unpublished, Published, Rejected, and Withdrawn. Each shows
  a count, preserves keyboard operation, and records selection in the URL.

### Statement detail: `/review/statements/[id]`

- Sticky orientation header: candidate, issue, current state, source.
- Primary pane shows summary and exact evidence quote.
- Evidence trace follows the required order:
  Statement → Evidence → Extraction → Normalized Content → Source Snapshot.
- Private editorial controls and timeline are visually contained in an
  “Internal editorial record” region.
- Each action uses a labelled form, visible focus, error summary, confirmation
  copy, and a disabled/pending state.
- Publishing and unpublishing show the exact public effect before confirmation.
- A public-preview link navigates in the same tab to the actual candidate page
  after a publish/unpublish result; browser Back returns to review.
- Rejected items remain discoverable through an explicit queue filter and retain
  their private timeline; they never appear on public pages.

### Responsive and accessible behavior

- Desktop uses a two-column evidence/timeline layout.
- Narrow layouts collapse to evidence first, controls second, timeline third.
- No horizontal scrolling at 320 CSS pixels.
- Logical heading order, landmarks, visible focus, field labels, error
  association, and status announcements target WCAG 2.2 AA.
- The full lifecycle is keyboard-operable.

## Deterministic Fixtures

`npm run db:prepare` creates five distinct synthetic statements:

- two synthetic statements awaiting review, reserved for the publication
  lifecycle and changes-requested/rejection lifecycle respectively;
- one synthetic reviewed-ready statement awaiting approval;
- one synthetic approved but unpublished statement;
- one synthetic actively published statement; and
- private notes, synthetic operator references, and history records containing
  sentinel text that negative public-route tests can search for.

All fixture timestamps and identifiers are fixed. `npm run db:prepare` first
validates and removes only the exact repository-local
`.data/election-explorer` fixture database directory, then rebuilds it from
ordered migrations and fixtures. The reset integration test may select only a
process-scoped descendant of repository-local `.data/test/`; any other override
is rejected before deletion. No glob or path outside those fixture roots can
widen the target. In-memory preparation remains idempotent for service replay
tests. Fixture actions use fixed request IDs so replay exercises the same
idempotency contract as the UI. A reset test proves
prepare → mutate/withdraw/reject → prepare restores the exact baseline counts,
phases, event digests, and public response.

## Verification Contract

- Unit and integration tests cover every allowed and invalid transition,
  transaction rollback, idempotent replay, append-only history, subject-digest
  mismatch—including evidence mutation between approval and publication—server
  timestamp ordering, terminal withdrawal, and migration backfill.
- Production-mode boundary tests prove `/review` and statement detail routes
  return HTTP 404 before route execution. Production-mode action tests prove
  every mutation rejects before
  opening a transaction and leaves statements, publications, and event counts
  unchanged.
- Public-query tests prove drafts, rejected statements, unpublished
  publications, internal notes, operator references, and all history rows are
  absent and cannot change public wording. The existing coverage-complete
  “No explicit public statement found in the sources reviewed.” path is used
  without consulting draft/editorial tables; this is the existing Vision rule,
  not a new absence methodology.
- End-to-end tests operate the review, approval, publication, unpublication,
  and public visibility lifecycle through the browser.
- A second contained browser test records `reviewed_changes_requested`, rejects
  that synthetic statement, confirms it remains available in the rejected queue
  filter, and confirms its sentinel content is absent publicly.
- Keyboard-only navigation, accessible names, focus visibility, mobile and
  desktop layouts, and browser console errors are checked.
- `npm run check` passes its existing coverage thresholds and production build.
- `npm run test:e2e` passes from a clean deterministic database.

## Success Criteria

1. A local operator can complete the full editorial lifecycle without a direct
   database command.
2. Every successful decision has an append-only timestamped event; invalid
   transitions preserve both current state and event counts.
3. Public candidate output contains only actively published, approved fixture
   evidence.
4. Private sentinel values never appear in public HTML, public query objects, or
   browser responses.
5. Migration from the verified Milestone 2 schema succeeds and preserves its
   published fixture.
6. The review experience passes automated checks, manual keyboard review,
   accessibility checks, responsive screenshots, and console inspection.

## Deliberately Deferred

- Authentication, permissions, accounts, sessions, and real operator identity.
- Production enablement or deployment.
- Live candidate or source data.
- Search, issue-browsing expansion, comparison, and ranking.
- Editing extracted summaries or evidence in the UI.
- Bulk review or bulk publication.
- Notifications, assignments, and multi-reviewer consensus.

### Data-flow shadow paths

```text
FORM INPUT -> SHAPE VALIDATION -> LOCAL-MODE GUARD -> TRANSACTION -> RESULT
    |                |                   |                |           |
    | missing        | empty/too long    | production     | stale     | success
    | wrong type     | invalid action    | disabled       | replay    | named error
    v                v                   v                v           v
 field error     field error          404/reject     no partial   status banner
                                                     writes
```

- Nil or missing input: Zod/form parser returns a field error; no transaction.
- Empty input: required reasons reject after trimming; no transaction.
- Error path: named transition, replay, policy, and persistence errors map to a
  page-level error summary; unexpected errors rethrow after contextual logging.
- Duplicate path: same request and same inputs returns the original result;
  same request with different inputs is a replay conflict.

### Error and rescue registry

| Method or codepath | Failure | Named error | Rescue action | Operator sees |
|---|---|---|---|---|
| `assertLocalReviewEnabled` | production or explicitly disabled mode | `LocalReviewDisabledError` | page returns not found; action rejects before DB access | Not found |
| `getReviewQueue` | database read failure | contextual database error | rethrow to Next.js error boundary with operation context | Review workspace unavailable |
| `getReviewStatement` | unknown statement ID | `EditorialRecordNotFoundError` | `notFound()` | Not found |
| `recordReview` | invalid note, reason, actor, or request ID | `EditorialInputError` | return field errors | Correct the labelled fields |
| `recordReview` | stale phase or illegal outcome | `EditorialTransitionConflictError` | rollback and reload current phase | Record changed; review current state |
| any mutation | request replay with changed inputs | `EditorialReplayConflictError` | rollback; preserve original event | Request conflicts with an earlier action |
| `approveStatement` | latest review is not ready | `EditorialTransitionConflictError` | rollback | Record a ready review first |
| `publishStatement` | evidence or attribution fails revalidation | `PublicationPolicyError` | rollback and show policy failure | Publication blocked |
| `publishStatement` | current subject digest differs from the latest approved editorial event | `EditorialSubjectChangedError` | rollback and require a fresh extracted statement and review | Approved evidence changed; publication blocked |
| `publishStatement` | active publication already exists | `EditorialTransitionConflictError` | return existing state without a new cycle | Already published |
| `unpublishStatement` | missing active cycle or reason | `EditorialTransitionConflictError` / `EditorialInputError` | rollback | Nothing unpublished; correct reason/state |
| `approveStatement` | reviewed subject digest no longer matches | `EditorialSubjectChangedError` | rollback and require fresh review | Evidence changed; review again |
| migration | checksum drift or backfill conflict | existing migration integrity/preparation errors | abort migration transaction | Preparation command fails with migration name |

No planned error is swallowed. Expected errors are visible in the form; unexpected
errors remain failures and include statement/action/request context without private
notes.

### Security and privacy review

| Threat | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Review route accidentally deployed | Medium | High | Production guard in page and every action, plus production-mode negative tests |
| Direct statement ID manipulation | Medium | Low locally | Parameterized lookup, fixture-only records, named not-found result |
| Script/markup in private notes | Medium | Medium | Length/type validation and React text escaping; notes never enter public payloads |
| Double submit or stale form | High | Medium | Request IDs, expected phase, unique constraints, transactional replay handling |
| Public query learns draft presence | High in current code | High | Remove all draft/editorial reads from public query and test response equality |
| Internal identifier or reason leaks | Low after boundary | High | Public query allowlist and sentinel-string route tests |

No dependency, credential, authentication, payment, or external API surface is
introduced.

### Interaction edge cases

| Interaction | Edge case | Planned behavior |
|---|---|---|
| Queue | zero items in a filter | Explain the state and link back to all records |
| Queue | deterministic items change after back navigation | Server-render current state; no optimistic cache |
| Form | double click | pending button state plus idempotent request ID |

### Code quality decision

- One `lib/editorial/workflow.ts` module owns transition logic.
- One `lib/editorial/queries.ts` module owns operator reads.
- Public and operator result types are separate and share no catch-all row shape.
- UI actions call named service methods; they do not issue SQL.
- The change will touch more than eight files because it is a verified vertical
  slice across migration, domain, UI, fixtures, public privacy, and tests. This
  is justified; adding parallel services or generic workflow abstractions is not.

### Transaction algorithm

For each mutation:

1. Assert local review mode before acquiring the database.
2. Parse and bound every form value; create the real/fixed service clock value.
3. Call `runStage` with `stage = editorial:<action>`,
   `idempotencyKey = requestId`, safe IDs plus the canonical input fingerprint,
   and a replay validator. The fingerprint binds actor, expected phase, and
   private note/reason; their plaintext is not written to `stage_runs`.
4. Inside its transaction, lock the statement row with `SELECT ... FOR UPDATE`,
   load the current phase and subject, compare `expectedPhase`, and calculate
   `MAX(sequence) + 1`.
5. Recompute the canonical subject digest at review, approval, and publication
   boundaries. Approval compares the latest `reviewed_ready` event; publication
   compares the latest `approved` event.
6. Apply the projection write and append all required event rows in that same
   transaction. A publication/unpublication failure rolls back both tables and
   the statement projection.
7. Return only stable IDs, action, phase, and sequence. Never return or log
   private note/reason text.

PGlite actions are serialized by the existing `WeakMap` queue; the row lock and
unique sequence constraint also state the database invariant explicitly. Tests
prove exact replay, changed-input conflict, stale phase, and concurrent duplicate
behavior.

### Migration detail

`drizzle/0004_editorial_review_controls.sql` will:

- replace only the named statement-status check to add `withdrawn`;
- run fail-fast preflight checks for every ambiguous legal Milestone 2 shape
  listed in the normative migration section;
- create both history tables, primary/foreign keys, row checks, unique replay
  keys, and `(statement_id, sequence)` ordering;
- backfill legacy approval and publication history before installing append-only
  triggers;
- use the immutable Milestone 2 payload digest for explicitly marked legacy
  approval/withdrawal subject records;
- update already-closed legacy publications to terminal `withdrawn` statement
  projection in the same transaction;
- assign the fixed migration reason only to a closed legacy row whose reason is
  null/blank; reject other inconsistent timestamp/state/reason shapes;
- create `active_publication_payloads` from immutable published/unpublished event
  existence and the referenced immutable approval event, never from mutable
  closure fields; and
- install shared `BEFORE UPDATE OR DELETE` rejection triggers last.

The existing one-publication-per-statement uniqueness remains unchanged. Runtime
uses the current `stableId("publication", statementId)` identity; SQL backfill
uses readable deterministic migration request IDs because Node hashing is not
available inside the SQL migration.

### Error-path verdict

All expected failures have named errors and a tested rescue:

- shape/bounds → field errors, zero database access;
