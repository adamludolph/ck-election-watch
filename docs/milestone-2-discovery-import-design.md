## Problem Statement

Milestone 1 proves that synthetic candidate content can move through capture,
normalization, extraction, approval, and publication without losing its evidence
chain. It does not yet prove how a candidacy or candidate-owned source enters
that pipeline.

Milestone 2 must add those two intake boundaries without using live data:

1. preserve and atomically import a saved official candidate roster; and
2. record, review, and accept a saved candidate-source discovery before capture.

The result must remain neutral and evidence-first. Import and discovery records
are provenance, not candidate claims.

## What Makes This Cool

The strongest trust property is not finding more URLs. It is making the system
show why a candidate and source were admitted at all.

After this slice, the local proof has two inspectable gates before any public
statement exists:

```text
official roster fixture
  -> preserved official import
  -> candidacy + status observation

manual discovery fixture
  -> proposed discovered source
  -> explicit acceptance
  -> registered source
  -> capture and existing evidence pipeline
```

A URL is not treated as candidate-owned merely because it contains a name, and
a parsed roster row is not silently promoted to canonical identity without the
saved official import that produced it.

## Constraints

- Use synthetic, committed fixtures only.
- Do not fetch a municipal site or any candidate site.
- Do not add credentials, environment variables, scheduled jobs, or deployment.
- Do not add candidate recommendations, inferred positions, scoring, ideology,
  comparison, social-media ingestion, or real candidate claims.
- Keep discovery review internal; do not add accounts, an admin route, or a
  review UI.
- Preserve the existing public publication payload and evidence semantics.
- Use the existing PGlite database, Drizzle schema contract, `runStage`
  transaction/idempotency pattern, deterministic IDs, and verification commands.
- Add a forward-only migration. Do not rewrite the shipped
  `drizzle/0000_evidence_pipeline.sql`.
- Keep the main test suite independent of live network access.

## Premises

1. Discovery is an admission-control record, not a crawler.
2. An accepted discovery is the only Milestone 2 path that may create a
   candidate content `Source`.
3. Proposed or rejected discovery results must not be capturable.
4. Official roster import and candidate-content ingestion remain separate
   contracts.
5. One official fixture is imported atomically: malformed input creates no
   import, candidacy, or observation rows.
6. The exact official fixture bytes, their SHA-256, content type, source URL,
   and observation time are durable domain data.
7. Later official status observations append history; they do not erase prior
   observations.
8. Existing statement attribution, approval, publication, and coverage wording
   are unchanged.
9. Discovery evidence and raw official payloads remain private operational data.

## Milestone 1 Retrospective Lessons

- Keep the fixture-backed happy path executable end to end; it exposes contract
  drift faster than broad scaffolding.
- Preserve raw evidence and immutable identifiers at the ingestion boundary so
  later publication can prove provenance without reconstructing it.
- Treat abstention, private operational data, and synthetic-only public copy as
  tested product behavior, not documentation-only promises.
- Design forward migrations against both empty databases and the shipped
  Milestone 1 fixture identities; deterministic IDs alone are not an upgrade
  strategy.

## Approaches Considered

### Approach A: Retrofit the two real intake gates

Add official import and discovery tables, two narrow services, deterministic
fixtures, and change fixture capture to require an already accepted source.

- Effort: M
- Risk: Medium
- Completeness: 9/10 for this milestone
- Pros:
  - proves both missing intake boundaries through the existing pipeline;
  - makes unauthorized capture structurally harder;
  - retains raw official provenance without inventing a generic adapter system;
  - keeps the public UI and publication contract stable.
- Cons:
  - requires a forward migration and localized changes to the demo orchestrator;
  - adds state-transition tests for discovery acceptance and rejection.
- Reuses:
  - `runStage`, `stableId`, PGlite migrations, existing candidate status history,
    website capture, and the current full verification suite.

### Approach B: Add a discovery review application

Build internal pages for importing rosters, proposing URLs, accepting or
rejecting discoveries, and viewing audit history.

- Effort: L
- Risk: Medium to high
- Completeness: 10/10 for editorial usability, but only 5/10 for the requested
  fixture-backed milestone because UI work dominates the intake contracts.
- Pros:
  - makes the workflow operable by a human without scripts;
  - exercises interactive state transitions.
- Cons:
  - requires authentication and authorization decisions that are explicitly
    outside scope;
  - expands browser, accessibility, and security surface before the data model
    is proven.
- Reuses:
  - the existing Next.js application and proposed intake services.

### Approach C: Build generic discovery and importer adapters

Introduce adapter interfaces, queues, URL classifiers, municipality-specific
configuration, and multiple fixture formats.

- Effort: L to XL
- Risk: High
- Completeness: broad, but premature
- Pros:
  - creates more future extension points immediately;
  - could support multiple municipalities and automated sources later.
- Cons:
  - guesses at live source behavior and configuration before one intake path is
    verified;
  - adds abstractions, retry policy, and operational semantics without evidence.
- Reuses:
  - little beyond the current stage runner and database.

## Recommended Approach

Choose Approach A.

It is the narrowest approach that proves the product boundary rather than
scaffolding future systems. The user-visible application should continue to show
the same synthetic evidence record, but that record will now be reproducibly
reachable only through preserved official import and accepted discovery.

The rejected alternatives are not future commitments. A review UI, live
municipal parser, automated discovery, and generalized adapters each require a
separate scope and approval decision.

## Domain Contract

### Official import

Add:

```text
official_import_runs
  id
  election_id
  source_url
  observed_at
  payload_sha256
  content_type
  encoding
  raw_payload
  imported_count
  created_at

candidacy_status_history
  official_import_run_id (nullable FK for compatibility)
```

Database constraints:

```text
official_import_runs
  unique(election_id, source_url, observed_at)

candidacy_status_history
  official_import_run_id -> official_import_runs.id
```

`raw_payload` is `bytea` and contains the exact committed fixture bytes.
`payload_sha256` is lowercase hexadecimal SHA-256 over those bytes, before JSON
decoding or validation. The fixture must be UTF-8 JSON with
`content_type = application/json` and `encoding = utf-8`. Byte-for-byte
preservation is required; a parsed or reserialized object is not a substitute.

`importOfficialRosterFixture(db, bytes)`:

- requires 1-262,144 bytes, hashes them, decodes strict UTF-8, parses JSON, and
  validates the entire versioned fixture before any domain write;
- uses election ID, source URL, and observed time as the logical import key;
- uses that logical key plus the exact payload hash as its stage idempotency
  key, so a changed-payload replay reaches the database conflict check rather
  than returning a cached stage result;
- returns the prior result when that key and payload hash match, but raises
  `OfficialImportConflictError` without mutation when the key exists with a
  different hash;
- creates the municipality, election, offices, people, candidacies, official
  import run, and linked status observations in one stage transaction;
- reconciles existing stable identities only under the key and immutable-field
  rules below;
- updates each candidacy's current status from the latest observation;
- returns the import run ID and imported candidacy IDs; and
- returns the prior successful stage result on an exact rerun.

The fixture remains synthetic. The source URL uses `example.invalid`.

Identity reconciliation is explicit:

| Entity | Stable key | Fields that must agree on replay |
|---|---|---|
| municipality | `id` | `slug`, `name` |
| election | `id` | `municipality_id`, `name`, `election_date` |
| office | `id` | `election_id`, `office_type`, `name`, `ward_slug` |
| person | `id` or municipality-scoped official person mapping | `display_name` |
| candidacy | `id` | `election_id`, `office_id`, `person_id`, `official_person_key`, `slug` |

An existing key with different immutable fields raises
`OfficialImportConflictError`; the full stage transaction rolls back. Candidacy
`status` is not immutable and changes only by appending official status history.

Each roster record supplies `upstreamKey`, a trimmed, case-sensitive,
1-128-character official record identifier. It is stored unchanged in
`candidacy_status_history.upstream_key`. Ownership evidence compares the
discovery value to that stored value by exact string equality; no name,
case-folding, or fuzzy match is allowed.

`upstreamPersonKey` is stored as `candidacies.official_person_key`. A later
candidacy in the same municipality reuses the one person already mapped to that
key. The review-hardening backfill reconstructs keys from preserved official
payloads before cached import replays can bypass reconciliation.

### Discovery

Add:

```text
discovery_runs
  id
  election_id
  method
  method_version
  input_sha256
  started_at
  completed_at

discovered_sources
  id
  discovery_run_id
  candidacy_id
  originally_observed_url
  canonical_url
  proposed_title
  proposed_source_type
  ownership_evidence
  status
  reviewed_at
  reviewer_note
  rejection_reason
  accepted_source_id
```

Database constraints:

```text
discovery_runs
  unique(election_id, method, method_version, input_sha256, started_at)

discovered_sources
  unique(discovery_run_id, candidacy_id, canonical_url)
```

The logical discovery-run key is election ID, method, method version, exact
fixture-byte SHA-256, and start time. A discovered-result key is discovery run,
candidacy, and canonical URL.

The discovery fixture supplies versioned natural-key evidence:

```typescript
type DiscoveryOwnershipInputV1 = {
  schemaVersion: "1";
  candidacy: {
    kind: "official-candidacy-link";
    officialImport: {
      sourceUrl: string;
      observedAt: string;
    };
    upstreamKey: string;
  };
  sourceAssociation: {
    kind: "candidate-page-self-identification";
    observedUrl: string;
    observedAt: string;
    excerpt: string; // 1-500 Unicode characters
  };
  note?: string; // 1-500 Unicode characters
};
```

The service resolves the official-import logical key plus `upstreamKey` inside
the record-stage transaction, verifies that the resolved observation belongs to
the same candidacy, and persists normalized evidence containing the resolved
official import run ID, candidacy ID, and upstream key. Fixtures never supply
internal IDs. Unknown fields, empty strings, and over-limit notes are rejected
before writes. `sourceAssociation.observedUrl` must exactly match the result's
originally observed URL. The excerpt is the bounded, synthetic,
human-reviewable evidence for the URL-to-campaign association; the official
link alone is not treated as source-ownership evidence.

`recordDiscoveryFixture(db, bytes)`:

- requires 1-65,536 UTF-8 JSON bytes and validates a versioned
  manual-discovery fixture;
- requires each candidacy to belong to the discovery run's election;
- preserves the observed URL separately from the canonical URL;
- records ownership evidence as bounded structured data;
- creates only `proposed` results; and
- is idempotent by fixture hash and run identity.

`proposed_title` is a trimmed 1-200-character string. `reviewer_note` is null
or a trimmed 1-500-character string. `rejection_reason` is null unless status is
`rejected`, where it is required and constrained to the three allowed reason
codes. Database checks enforce those status-dependent nullability rules.

`Source` reconciliation uses the existing unique key
`(candidacy_id, canonical_url)`. An existing row is reusable only when its
`source_type`, `title`, `attribution_policy`, and `active` fields exactly match
the accepted discovery contract. Mismatched metadata raises
`DiscoverySourceConflictError` without mutation.
Later discovery runs may link another accepted result to the same matching
`Source`; rediscovery creates audit history, not duplicate source identities.

`acceptDiscoveredSource(db, discoveredSourceId, now, note?)`:

- runs as one `runStage` transaction so the source and discovery transition
  either both commit or both roll back;
- evaluates source reconciliation and capture eligibility inside that
  transaction, avoiding a preflight/read-then-write gap;
- accepts a `proposed` website discovery;
- creates or reconciles one `Source` with the discovered title,
  `source_type = website`, the discovered canonical URL,
  `attribution_policy = candidate_owned`, and `active = true`;
- links the accepted source back to the discovery result;
- records review time and an optional neutral reviewer note of at most 500
  Unicode characters; and
- returns the original result without changing review time or note when the
  discovery is already accepted with the same source.

`rejectDiscoveredSource(db, discoveredSourceId, now, reason, note?)`:

- runs as one `runStage` transaction;
- rejects a `proposed` result;
- records one reason from `ownership-not-established`, `duplicate`, or
  `out-of-scope`, an optional neutral note of at most 500 Unicode characters,
  and review time;
- never creates a `Source`; and
- returns the original result without changing review time, reason, or note on
  an identical rejected-state replay.

Acceptance and rejection are terminal for this slice:

| Current state | Requested action | Result |
|---|---|---|
| `proposed` | accept | atomically create/link source and set `accepted` |
| `proposed` | reject | atomically set `rejected`; create no source |
| `accepted` | same accept replay | return original result unchanged |
| `rejected` | same reject replay | return original result unchanged |
| `accepted` | reject | `DiscoveryTransitionError`; no mutation |
| `rejected` | accept | `DiscoveryTransitionError`; no mutation |

Reopening or superseding a decision is deferred.

Database checks enforce:

```text
proposed:
  reviewed_at, reviewer_note, rejection_reason, accepted_source_id are null
accepted:
  reviewed_at and accepted_source_id are non-null; rejection_reason is null
rejected:
  reviewed_at and rejection_reason are non-null; accepted_source_id is null
```

`discovery_runs` has no second lifecycle. A row represents one successfully
completed immutable fixture run; `started_at` and `completed_at` describe it,
while running/failed attempts remain solely in `stage_runs`.

### Capture gate

Change `captureWebsiteFixture` to receive `sourceId`, not candidacy, title, and
canonical URL fields that allow it to create a source implicitly.

Before `runStage` may return a cached result, it checks current eligibility.
Inside the capture-stage transaction it repeats the same query to close the
preflight-to-write gap. Before writing bytes both checks must prove that:

- the source exists and is active;
- its type is `website`;
- its attribution policy is `candidate_owned`;
- it is linked from an accepted discovered source; and
- the requested canonical URL equals the registered canonical URL.

Failure records a failed capture stage and creates no snapshot or observation.
A replay of a previously successful capture is denied if the source has since
become inactive or otherwise ineligible.

## Fixed Fixture Outcomes

`tests/fixtures/official-candidates.json` becomes a versioned official roster:

- one synthetic Chatham-Kent mayoral candidacy;
- source URL `https://example.invalid/municipal-election/candidates`;
- observation time `2026-07-24T16:00:00.000Z`; and
- status `registered`.

`tests/fixtures/discovered-sources.json` contains one synthetic manual discovery:

- the deterministic `candidacy_demo_2026_mayor` row returned or reconciled by
  the official import, whose public slug is `demo-candidate`;
- observed and canonical campaign-platform URLs under `example.invalid`;
- proposed type `website`;
- candidate-ownership evidence that cites the saved official roster identity;
- discovery time before the existing saved website capture.

The demo pipeline records and accepts that discovery, then passes its source ID
to the unchanged normalize, extract, approve, publish, and coverage stages.

Tests create additional inline fixtures to prove rejection, cross-election
blocking, identity conflict handling, and capture denial without adding more
committed candidate examples.

Both fixture schemas are strict: unknown keys are rejected at every object
level. The official fixture contains a schema version, municipality slug/name,
election name/date, source URL, observation time, offices, and roster records.
Every roster record contains a unique 1-128-character `upstreamKey`, unique
1-128-character `upstreamPersonKey`, display name, candidacy slug, status, and
office reference. Duplicate upstream keys, person keys that resolve to
conflicting names, office references, or candidacy slugs reject the whole
fixture.

Internal IDs are never accepted from fixture input. They are derived with
`stableId` from trusted normalized fields:

```text
municipality = slug
election     = municipality ID + election date
office       = election ID + office type + ward slug-or-empty
person       = municipality ID + upstreamPersonKey
candidacy    = election ID + upstreamKey
```

Slug-like fields are lowercase ASCII with explicit length bounds; names retain
validated Unicode. Normalization occurs before ID derivation and is covered by
fixture-schema tests.

Current candidacy status is selected by `observed_at DESC,
official_import_run_id DESC NULLS LAST, id DESC`. An out-of-order older import appends
history but cannot replace a newer current status. A different status for the
same candidacy and exact `observed_at` is an
`OfficialImportConflictError`; an identical observation is an idempotent replay.

## Failure and Invariant Registry

| Path | Required behavior |
|---|---|
| malformed official fixture | reject before writes |
| one malformed roster row | reject the whole import |
| exact official rerun | return the same import and candidacy IDs |
| conflicting stable identity | reject without overwriting stored identity |
| later official status | append history and expose the latest status |
| malformed discovery fixture | reject before writes |
| cross-election candidacy | reject the whole discovery run |
| proposed discovery capture | reject; no snapshot |
| rejected discovery capture | reject; no source and no snapshot |
| accepted discovery | create exactly one source and durable acceptance link |
| exact acceptance rerun | return the same source |
| later matching rediscovery | link the new accepted result to the same source |
| opposite terminal transition | reject without changing the first decision |
| partial review write failure | roll back both source and discovery changes |
| capture URL mismatch | reject; no snapshot |
| existing publication path | produce the same public payload and wording |

### Step 0: Scope and Premise Verdict

The plan solves the correct next problem. Milestone 1 already proves the
evidence-to-publication path; Milestone 2 should prove how identities and
candidate-owned URLs enter that path. Doing nothing leaves two hidden trust
assumptions: that a roster object is official and that a URL belongs to a
candidate.

The minimum credible slice is exactly:

```text
saved official bytes -> official import provenance -> candidacy observation
saved discovery bytes -> proposed URL -> explicit acceptance -> registered source
registered source -> existing fixture capture and evidence pipeline
```

No part of the public statement, review, publication, or UI contract needs to
change. The plan introduces two domain services: one extends the existing
official importer and one owns discovery review. More than eight files will
change because migration, fixture, tests, and documentation must move together,
but adding a framework or UI would increase complexity without strengthening
the proof.

### 1. Architecture Review

```text
OFFICIAL INTAKE
official-candidates.json bytes
  -> size/hash/UTF-8/JSON/schema validation
  -> runStage("official-import")
      -> official_import_runs
      -> municipality/election/office/person/candidacy reconciliation
      -> candidacy_status_history

DISCOVERY INTAKE
discovered-sources.json bytes
  -> size/hash/UTF-8/JSON/schema validation
  -> runStage("discovery-record")
      -> discovery_runs
      -> discovered_sources(proposed)
  -> runStage("discovery-accept")
      -> conditional proposed-state transition
      -> sources(active website, candidate-owned)
      -> discovered_sources(accepted, accepted_source_id)

EXISTING PIPELINE
accepted source
  -> capture -> normalize -> extract -> approve -> publish -> public DTO
```

Byte bounds, hashing, UTF-8 decoding, JSON parsing, and strict schema validation
occur before `runStage` writes its running marker. Such malformed inputs create
no stage or domain rows. Valid inputs enter `runStage`; all domain validation and
writes for one logical operation occur inside its transaction, so identity,
election, ownership, state, or logical-key conflicts produce a failed stage
attempt but no partial domain write. Acceptance must use a conditional state
update, not a read-then-write transition, so two callers cannot both win.

`runStage` is hardened once for all existing callers: operations on one PGlite
instance enter a per-instance single-flight queue, and domain execution uses
PGlite's callback transaction API with the transaction object passed to the
stage callback. Success lookup, attempt allocation, running-marker insertion,
transaction execution, and failure-marker update therefore cannot interleave on
the shared connection. `BEGIN` is never issued outside the guarded `try`.
Cross-process coordination remains outside this local PGlite milestone.

The migration runner currently hard-codes `0000`. It must move to an explicit,
ordered migration manifest and apply each immutable file by name and digest.
Each unapplied migration SQL file and its ledger insert execute in the same
PGlite transaction. Tests must prove both an empty database and a database with
only `0000` plus its correct ledger row reach the same Milestone 2 schema.

The first forward migration also adds a unique index on
`candidacy_status_history(candidacy_id, observed_at)`. This converts the
equal-timestamp conflict rule from a service convention into a database
invariant while preserving the existing append-only history. Before creating
the index, `0001` checks for duplicate candidacy/timestamp groups that were legal
under `0000` and raises a deterministic migration error if any exist. It does
not choose a winner or rewrite evidence. The migration runner rolls back the
file and ledger row; the operator must review the contradictory local fixture
data before retrying.

State machines:

```text
official import key
  absent -> succeeded
  succeeded + same hash -> same result
  succeeded + different hash -> CONFLICT

discovered source
  proposed -> accepted
           -> rejected
  accepted -> accepted replay
           -X rejected
  rejected -> rejected replay
           -X accepted

source capture eligibility
  no source / inactive / wrong type / wrong relationship / no accepted discovery
    -> DENIED
  active candidate-owned website linked to accepted discovery
    -> ELIGIBLE
```

At 10x fixture volume, validation and insertion remain linear and bounded by the
262,144-byte official and 65,536-byte discovery caps. At 100x, the all-or-nothing
roster transaction becomes the first pressure point. That is acceptable for a
local fixture milestone; chunking would weaken atomicity and invent production
requirements.

There are no endpoints, credentials, jobs, external calls, or production
integration points. Rollback is code revert plus recreation of the explicitly
identified local `.data/election-explorer` database from committed fixtures.
The forward migration is not reversed against a retained database.

### 2. Error and Rescue Map

| Method/codepath | Failure | Named error | Rescue action | User impact |
|---|---|---|---|---|
| `applyMigrations` | migration digest changed | `MigrationIntegrityError` | stop preparation; preserve DB | `db:prepare` fails |
| `applyMigrations` | ordered migration fails | `DatabasePreparationError` | add migration name/cause; stop | `db:prepare` fails |
| `importOfficialRosterFixture` | empty, oversized, invalid UTF-8/JSON/schema | `OfficialImportValidationError` | reject before domain writes | import unavailable |
| `importOfficialRosterFixture` | existing logical key has different bytes | `OfficialImportConflictError` | rollback | prior record preserved |
| `importOfficialRosterFixture` | stable entity fields disagree | `OfficialImportConflictError` | rollback full batch | prior identities preserved |
| `recordDiscoveryFixture` | empty, oversized, invalid JSON/schema | `DiscoveryValidationError` | reject before domain writes | discovery unavailable |
| `recordDiscoveryFixture` | candidacy/import evidence mismatch | `DiscoveryValidationError` | rollback full run | no proposals recorded |
| `acceptDiscoveredSource` | missing result or invalid transition | `DiscoveryTransitionError` | rollback | decision unchanged |
| `acceptDiscoveredSource` | existing source metadata conflicts | `DiscoverySourceConflictError` | rollback | no acceptance/source change |
| `rejectDiscoveredSource` | missing result, invalid reason, opposite terminal state | `DiscoveryTransitionError` | rollback | decision unchanged |
| `captureWebsiteFixture` | source is not accepted/eligible or URL differs | `SourceCaptureValidationError` | fail stage; no snapshot | source unavailable |
| `prepareDemoDatabase` | any intake stage fails | `DatabasePreparationError` | stop pipeline with named cause | local demo not prepared |

No rescue substitutes a guessed identity, silently skips a roster row, accepts
a URL, or continues into capture. Persisted stage error messages are bounded
safe summaries and do not include raw payloads or ownership evidence.

### 3. Security and Threat Model

| Threat | Likelihood | Impact | Mitigation |
|---|---|---|---|
| oversized fixture exhausts memory | Low | Medium | byte caps before parse |
| malformed Unicode/JSON produces divergent identity | Medium | Medium | strict UTF-8, versioned schema, exact keys |
| SQL injection through fixture strings | Low | High | parameterized queries only |
| URL spoofing admits wrong source | Medium | High | exact URLs plus explicit self-identification evidence and official-observation link |
| state-race accepts and rejects same result | Low | High | single-flight stage execution plus conditional transition |
| private intake evidence leaks publicly | Low | High | public DTO negative tests; no public query joins |
| raw error text leaks fixture data | Low | Medium | named safe error summaries |

No new dependency, secret, auth boundary, network target, or executable content
is introduced. URLs are stored, never fetched by import/discovery tests.

### 4. Data Flow and Edge Cases

```text
BYTES -> BOUNDS -> HASH -> UTF-8 -> JSON -> ZOD -> RECONCILE -> TRANSACTION -> IDS
  |        |        |       |       |      |          |             |
 nil     empty    stable  invalid malformed unknown  conflict      rollback
  +--------+--------+-------+-------+------+----------+-------------+
                  named failure; no downstream domain rows
```

Every new input has explicit nil/empty/wrong-type/oversized/malformed paths.
Every persistence path has exact-rerun, conflicting-rerun, missing-FK, and
opposite-state coverage. There is no new user interaction. Existing candidate
page success, absence, and 404 behavior remain the browser regression surface.

### 5. Code Quality Review

The implementation should add one discovery module and extend existing
candidate, capture, migration, schema, error, and demo-orchestration modules.
Do not introduce repositories, adapters, base classes, queues, event buses, or
dependency injection.

Shared byte decoding/hashing may be a small pure helper only if both import
paths use the identical contract. Identity reconciliation remains explicit per
entity; compressing it into a generic upsert would hide conflict semantics.
Each service accepts an explicit `PGlite` client and parsed timestamps, and none
opens connections or reads fixture paths.
